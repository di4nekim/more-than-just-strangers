01

Where it's at

This is best read as an advanced prototype with real cloud infrastructure, not a shippable product. The full journey — land → sign in → matchmake → 36-question chat → congrats — is wired up, and there are genuinely thoughtful touches: specific Firebase auth error messages, an IO-error recovery screen, confirm-before-end dialogs, and reconnection handling.

But it sits on a codebase that has accreted heavily. The data/auth layer has concrete correctness and authorization defects, the UI still ships hardcoded placeholder identities, and the safety nets meant to catch this — TypeScript and the test suite — are themselves compromised. The single most urgent item isn't a code bug: live production credentials sit in cleartext on disk and should be treated as compromised and rotated now.

Update, 2026-09-15. Since the audit: all five blockers were fixed, the backend races and presence bugs were closed with conditional writes, the frontend data-flow bugs were repaired, CORS/CSP were tightened, and the test suite was rebuilt so it exercises the real code — 256 tests passing, 0 failing, up from 156 / 73. Everything below carries a status chip. Credential rotation is being handled outside this report.

Ship blockers

must clear before deploy
Critical

Live production credentials in plaintext on disk

✓ verifiedcode hardened · rotation tracked separately
.env.production · .env.local · firebase mtjs-prod secrets/…adminsdk-fbsvc…json · mtjs firebase key.json

A real AWS IAM secret key and the Firebase Admin service-account private key for mtjs-prod exist in cleartext. Mitigating: the .env files are gitignored and not in git history, and the AWS secret isn't a NEXT_PUBLIC var (not in the client bundle). Risk remains — key material is trivially leaked via an accidental add, zip, backup, or vercel env push.

Fix → Rotate now: deactivate the IAM key (issue a scoped least-privilege replacement, ideally Vercel OIDC) and regenerate the Firebase Admin key. Remove the secret files from the tree; keep only a redacted .env.example; store prod values in Vercel encrypted env vars.

Critical

endConversation lambda exports no handler — ending a chat is deploy-broken

✓ verifiedfixed · 1486b73
server/lambdas/endConversation/index.js:28 · template.yaml:468 (Handler: endConversation/index.handler)

The file defines only handlerLogic; there is no exports.handler, yet the SAM template (and the lambda's own e2e test) require index.handler. AWS fails to load an undefined handler. It also never sets event.userInfo (no auth wrapper), so it would throw even if exported. Compounded: it never clears either user's chatId, so ending would leave both users permanently "already in a conversation."

Fix → Add an authenticated exports.handler (mirror setReady/updatePresence), clear chatId/ready/questionIndex on both participants, and add a deploy smoke test that every Handler: path resolves to an exported function.

High

IDOR — any authenticated user can read any conversation

✓ verifiedfixed · 1486b73 + 714105a
src/app/api/chat/[chatId]/messages/route.js:10 · sendMessage/index.js · syncConversation/index.js (no auth wrapper)

The messages route validates the Firebase token but never checks the caller is a participant before querying DynamoDB — and chatIds are guessable sorted userA#userB pairs. Worse on the lambda side: sendMessage has no participant check (message injection) and syncConversation has no auth wrapper at all.

Fix → Before any chat-scoped read/write, resolve participants and assert user.uid is one of them (403 otherwise). The chat-context route already does this — reuse it as the pattern.

High

Unauthenticated /api/debug routes leak config & init the Admin SDK

✓ verifiedfixed · 1486b73 (404 in production)
src/app/api/debug/env/route.js · src/app/api/debug/firebase-auth/route.js (untracked)

Both routes exist, are untracked, and middleware applies no auth. env reports which secrets are set, the exact FIREBASE_PRIVATE_KEY length, node/platform, and calls firebase-admin init per request; firebase-auth echoes internal error messages. The vercel.json redirect for /debug/* does not match /api/debug/*.

Fix → Delete src/app/api/debug before deploy, or gate behind NODE_ENV!=='production' + a secret. Never return env presence, key lengths, or raw errors to unauthenticated callers.

High

Type-checking disabled for the production build

✓ verifiedfixed · 1486b73 (build verified)
next.config.mjs:3-5 (uncommitted) · tsconfig.json:6-7 (strict:false)

A working-tree change sets typescript.ignoreBuildErrors: true on top of strict:false, so the Vercel prod build type-checks nothing — right before a prod deploy, and while the project is effectively JS (one .ts file, not even the imported one). This masks real defects in auth/validation paths.

Fix → Revert ignoreBuildErrors and fix the underlying errors, or scope + track the suppression as explicit debt. Then decide: commit to TS (incremental + strict) or drop the TS surface entirely.

05

UX inconsistencies & friction

  • Placeholder identities everywhere. QUINCEY/JOHNATHAN on every message, "Quincey" on congrats, "5* NEW MESSAGES" always — the app reads as an unfinished mockup to a real user.
  • Navigation is inconsistent & partly unreachable. Two sign-in routes disagree on where to send users; post-login lands on the marketing page; sign out / home / end-chat are hover-only, so they fail on touch and keyboard. hover-only controls now reveal on focus; routing still open
  • No escape from "Finding a match…". The spinner has no cancel or timeout — a user can hang forever — and there's no clear disconnected/reconnecting state.
  • Paid-for feedback is invisible. Typing-indicator and presence systems are imported but never rendered (and the typing module is deprecated yet still in the path).
  • Responsiveness gap. Fixed 50/50 split layouts and side-by-side congrats panels will break at phone widths.
  • Off-by-one completion. Reaching question 36 jumps to congrats, apparently skipping the final question. fixed
  • Worth preserving. Specific Firebase auth error messages, the IO-error recovery screen, confirm-before-end dialogs, and reconnection handling are genuine bright spots.

Method. Audit (2026-09-14): a read-only, 8-agent workflow reviewed 7 dimensions in parallel (architecture, security, frontend, backend, config, testing, UX) → 110 raw findings → one deduplicated, ranked synthesis; the load-bearing critical/high claims were re-verified against the source by hand. Remediation (2026-09-15): blockers fixed by hand, the remaining worklist by a 5-agent workflow over disjoint files, every touched lambda checked to load and export its handler, lint and the production build verified. Test suite: pre-existing failures diagnosed one by one, obsolete suites removed rather than skipped, new suites written at the real handler contracts, and every gated suite re-audited (section 03).

Caveats. The two remaining gated suites (endConversation e2e, API HTTP) were repaired to the current contracts but could not be run here — they need a real Firebase ID token and live infrastructure, so treat them as unverified until run with ENABLE_INTEGRATION_TESTS=true FIREBASE_TEST_ID_TOKEN=…. The conversationMetadata field names were inferred from the client code and should be confirmed against a live conversationStarted/currentState payload. After a chat starts, WebSocketProvider keeps React work queued long enough that act() never settles in tests — a possible runaway effect worth profiling in the browser. The config/deploy reviewer in the original audit returned a malformed result; its concerns were covered by the other reviewers.
